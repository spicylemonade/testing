# Runtime monitor note for item_018

- Scope checked: `research_rubric.json` item_018, `results/experiments/controls/summary.json`, all 10 control run JSONs, `results/experiments/order_668_64m/summary.json`, and all 5 order run JSONs. All referenced run files are present, and all 15 run JSONs carry a `canonical_fingerprint`.
- Summary-to-run consistency is clean for the fields that are actually reported. `wall_seconds`, `objective_evaluations`, exact-hit/best-objective fields, and the order-668 completed/requested restart counts all match the run files. The control summary is lossy for restart accounting because it does not expose `restart_statistics`; those counts are only present in the per-run JSON.
- Wall-clock profile: the 10 control runs are all short (0.034-0.082 s each, 0.600 s total). The `order_668_64m` batch totals 2.548 s, and H1 alone accounts for 2.129 s of that total (~84%) despite only 32 objective evaluations. The other order runs stay in the 0.079-0.144 s range with 26-80 evaluations.
- Restart accounting: requested restarts are 3 everywhere. Controls complete 3/3 in 8 of 10 runs; the exceptions are `control_n5_q0/tabu` at 2/3 with 80 evaluations and `control_n7_q0/simulated_annealing` at 1/3 with 80 evaluations. In `order_668_64m`, H1 and stochastic hillclimb complete 3/3, while greedy, tabu, and simulated annealing complete only 1/3 while consuming the full 80-evaluation budget. The trace restart IDs agree with those counts, so this looks like budget exhaustion inside early restarts rather than missing run data.
- Trace shape is method-dependent and should not be used as a proxy for evaluation count. H1 logs stepwise CA state (`step`, `active_packets`, `active_lag_count`, `max_coupled_pressure`) and its trace length is close to evaluation count; the baseline methods log sparse snapshots or accepted moves (`packet` optional), so 80 evaluations can still yield a 2-3 row trace. Example: `order_668_64m` greedy and simulated annealing both show two identical restart-0 snapshots after 80 evaluations.
- Audit caveat: the last trace row is not the reported best/terminal objective. The control summary's `terminal_support` aligns with run `objective_summary` (best found) rather than `.trace[-1]`; for example, `control_n5_q0/greedy` reports `terminal_support = 0`, but the last trace row in restart 2 still has support 1. For runtime or restart-end auditing, use `restart_statistics` plus per-restart trace segmentation, not the overall trace tail.
