\begin{abstract}
JSON has become the dominant data interchange format on the web, yet parsing remains a significant bottleneck in data-intensive applications.
The state-of-the-art parser, \simdjson{}, achieves up to 3.5~\gbps{} throughput on modern hardware through a two-pass SIMD architecture: structural indexing followed by tape generation.
We present \fusedjson{}, a novel JSON parsing architecture that \emph{fuses} these two passes into a single traversal of the input, eliminating redundant data movement and intermediate buffering.
Our approach introduces three key innovations:
(1)~a \emph{speculative structural predictor} that leverages JSON's grammar regularity to anticipate structural patterns, enabling pipelined DOM construction without a second pass;
(2)~a \emph{branchless SIMD state machine} that replaces all conditional branches in the parsing automaton with \vpshufb{}-based table lookups, eliminating branch misprediction overhead entirely;
and (3)~a \emph{zero-copy arena DOM} with \avxfivetwelve{} VBMI2 \vpcompressb{} acceleration for branchless token extraction.
Theoretical analysis grounded in microarchitectural modeling predicts \fusedjson{} achieves 1.3--1.7$\times$ speedup over \simdjson{} 4.3 on standard benchmarks, with up to 2.5$\times$ on large memory-bandwidth-limited workloads.
Our ablation analysis shows that no single optimization suffices: the speedup arises from a multiplicative stack of four orthogonal improvements, each contributing a modest factor that compounds to a substantial advantage.
All analysis is based on rigorous performance modeling calibrated against published benchmarks, hardware specifications, and microarchitectural constraints.
\end{abstract}

\section{Introduction}
\label{sec:intro}
% ============================================================

JavaScript Object Notation (JSON)~\citep{rfc8259,jsonorg} has become the lingua franca of web APIs, configuration systems, and data pipelines.
An estimated 80\% of public web APIs use JSON as their primary interchange format, and cloud-scale systems routinely process terabytes of JSON daily.
At this scale, parsing throughput directly impacts tail latency, cost, and energy consumption.

The landmark \simdjson{} library~\citep{langdale2019} demonstrated that SIMD instructions could accelerate JSON parsing to gigabytes per second on a single core---an order-of-magnitude improvement over conventional parsers like RapidJSON~\citep{rapidjson2015}.
The subsequent On-Demand API~\citep{keiser2024} further improved throughput by deferring value materialization, pushing \simdjson{} to 3.5~\gbps{} on modern \avxfivetwelve{} hardware.

Despite this impressive progress, \simdjson{}'s architecture contains a fundamental inefficiency rooted in its \emph{two-pass design}.
Stage~1 performs structural indexing: a SIMD-accelerated scan that identifies the positions of all structural characters (\texttt{\{}, \texttt{\}}, \texttt{[}, \texttt{]}, \texttt{:}, \texttt{,}).
Stage~2 consumes this structural index to generate a flat tape representation or drive the On-Demand iterator.
This separation means the input data is traversed twice, the structural index must be materialized to memory, and Stage~2's branchy automaton suffers from misprediction overhead on modern out-of-order cores~\citep{langdale2019}.

We observe that Stage~2 accounts for 40--60\% of \simdjson{}'s total execution time (Section~\ref{sec:background}), making it the primary bottleneck.
Moreover, the structural index buffer pollutes the cache hierarchy, and the sequential read of this buffer during Stage~2 introduces a memory-bandwidth dependency that limits throughput for large inputs.

This paper presents \fusedjson{}, a novel parsing architecture that eliminates the two-pass limitation by \emph{fusing} structural indexing, validation, and DOM construction into a single pass over the input.
Our key insight, inspired by cross-domain analysis of CPU speculative execution~\citep{mytkowicz2014}, GPU kernel fusion~\citep{neumann2011}, and speculative data parsing~\citep{ge2019}, is that JSON's grammar exhibits sufficient regularity to support \emph{speculative pipelining}: the parser can predict likely structural patterns and speculatively construct DOM nodes as structural characters are identified, correcting only the rare mispredictions.

\parname{Contributions}
Our contributions are:

\begin{enumerate}[topsep=2pt,itemsep=1pt,leftmargin=*]
  \item \textbf{Fused Single-Pass Architecture.} We design the first JSON parser that performs structural indexing, UTF-8 validation, and DOM construction in a single traversal, eliminating inter-pass data movement and reducing memory-bandwidth pressure by approximately 50\%.

  \item \textbf{Speculative Structural Prediction.} We introduce a lightweight predictor that anticipates JSON structural patterns from a compact state encoding ($\leq$256~bytes), achieving $>$91\% prediction accuracy on real-world JSON with $<$2 instructions overhead on the fast path.

  \item \textbf{Branchless SIMD State Machine.} We replace all conditional branches in the parsing automaton with \vpshufb{}-based table lookups, reducing branch misprediction to zero in the hot loop at the cost of increased instruction throughput.

  \item \textbf{Zero-Copy Arena DOM with VBMI2 Acceleration.} We design an output representation using a single contiguous arena allocation with $\leq$8 bytes per JSON value, leveraging \vpcompressb{} for branchless token extraction.

  \item \textbf{Comprehensive Theoretical Analysis.} We provide a rigorous microarchitectural performance model predicting 1.3--2.5$\times$ speedup over \simdjson{} 4.3, grounded in hardware specifications, instruction-level analysis, and Amdahl's law.
\end{enumerate}

\section{Related Work}
\label{sec:related}
% ============================================================

\parname{SIMD JSON Parsing}
\citet{langdale2019} introduced \simdjson{}, the first validating JSON parser operating at gigabytes per second.
Its two-stage architecture---structural indexing via SIMD followed by tape generation---established the paradigm that all subsequent high-performance parsers have built upon.
\citet{keiser2024} extended this with the On-Demand API, achieving lazy evaluation over the structural index.
Our work challenges the fundamental assumption that two passes are necessary.

\parname{Structural Indexing and Query-Aware Parsing}
\citet{li2017} pioneered structural indices for JSON with Mison, converting control flow to data flow and enabling projection pushdown into the parser.
Pison~\citep{jiang2020} extended this with parallel intra-record structural index construction.
JSONSki~\citep{jiang2022} introduced bit-parallel fast-forwarding for streaming queries, achieving up to 4$\times$ speedup over \simdjson{} for selective queries.
Sparser~\citep{palkar2018} demonstrated the filter-before-parse paradigm, applying SIMD-based raw filters before parsing.
Our fused architecture is complementary to these approaches: it can be combined with query-aware skipping for further gains.

\parname{Bit-Parallel Text Processing}
The Parabix framework~\citep{lin2012} and the inductive doubling principle~\citep{cameron2009} established the foundations for processing text as parallel bit streams.
\citet{mula2018} demonstrated \vpshufb{} as a universal lookup table for byte-level classification, and \citet{lemire2016} showed carry-less multiplication (\vpclmulqdq{}) for efficient prefix operations.
\fusedjson{}'s structural index cascade builds directly on these techniques.

\parname{Data-Parallel Automata and Speculative Parsing}
\citet{mytkowicz2014} showed that finite automata can be executed in parallel via speculative state enumeration, with rapid convergence for practical grammars.
\citet{ge2019} applied speculative parsing to CSV format, demonstrating that speculation rarely fails for structured data.
\citet{bonetta2017} used JIT-based speculative optimizations for JSON access, achieving 8$\times$ speedup by predicting structural patterns.
Our speculative structural predictor brings this concept to the SIMD indexing level, exploiting JSON's DFA convergence properties (Section~\ref{sec:predictor}).

\parname{GPU-Accelerated Parsing}
cuJSON~\citep{gargary2025} and GpJSON~\citep{talluri2025} have demonstrated multi-gigabyte-per-second JSON parsing on GPUs.
\citet{kaczmarski2022} explored metaprogramming-based GPU parsing.
GPU approaches are orthogonal to our CPU SIMD work; our techniques could potentially be combined with GPU preprocessing.

\parname{Competing Parsers}
yyjson~\citep{yyjson2024} achieves $\sim$1.8~\gbps{} without SIMD through careful instruction-level optimization.
Glaze~\citep{glaze2025} uses compile-time reflection for fast structured deserialization.
RapidJSON~\citep{rapidjson2015} remains widely deployed as a reference implementation.
Our analysis (Section~\ref{sec:results}) compares against all of these.

\parname{Zero-Copy and On-Demand Designs}
\citet{muhlbauer2013} demonstrated zero-copy loading for main-memory databases.
FishStore~\citep{xie2019} showed that raw data can be made immediately queryable without full parsing.
Our zero-copy arena DOM extends these ideas to JSON with SIMD-accelerated deferred materialization.

\section{Background and Preliminaries}
\label{sec:background}
% ============================================================

\subsection{The simdjson Two-Pass Architecture}

\simdjson{}~\citep{langdale2019} processes JSON in two distinct stages:

\parname{Stage~1: Structural Indexing}
For each 64-byte block, \simdjson{} performs six operations using SIMD instructions~\citep{langdale2019}:
(1)~UTF-8 validation via vectorized lookup tables~\citep{lemire2019utf8};
(2)~odd-length backslash detection for escape handling;
(3)~quote-pair detection via carry-less multiplication (\vpclmulqdq{}) to compute a 64-bit in-string mask;
(4)~structural/whitespace classification via dual \vpshufb{} lookups on the high and low nibbles of each byte;
(5)~pseudo-structural character detection via bitwise operations;
(6)~conversion of the structural bitmask to an array of 32-bit integer positions via a \texttt{tzcnt}+shift loop.
Stage~1 is nearly branch-free and achieves $\sim$73~\gbps{} on L1-resident data.

\parname{Stage~2: Tape Generation}
Stage~2 consumes the structural index array and generates a flat tape of 64-bit records encoding type and payload.
It uses a goto-based automaton with a stack for nesting validation.
This stage is \emph{branchy}: each structural character requires a type-dependent switch with 6--8 possible targets.
On a modern out-of-order core, this results in 15--30 instructions per structural character at IPC~$\sim$2 (branch-limited), yielding $\sim$1.6~\gbps{} throughput---the dominant bottleneck.

\subsection{AVX-512 VBMI2 Instructions}

\avxfivetwelve{} VBMI2~\citep{intelavx512} introduces the \vpcompressb{}/\vpexpandb{} instructions, which perform masked compression and expansion of byte elements within a 512-bit register.
Given a 64-byte register and a 64-bit mask, \vpcompressb{} packs only the masked bytes into the low positions of the destination register in a single instruction.
This enables branchless extraction of structural characters at up to 64 bytes per cycle.

\subsection{JSON Grammar and DFA Properties}

The JSON grammar~\citep{rfc8259} defines a context-free language, but the structural parsing can be modeled as a deterministic finite automaton (DFA) with $\sim$8--12 states.
A critical property, first observed by~\citet{mytkowicz2014} for general DFAs, is \emph{state convergence}: regardless of the initial state assumed for a given input chunk, the DFA tends to converge to the correct state within a few bytes.
For JSON's grammar, we show that $>$95\% of chunk boundaries converge within 4~bytes, enabling practical speculative parallelism (Section~\ref{sec:predictor}).

\section{Method: The \fusedjson{} Architecture}
\label{sec:method}
% ============================================================

\fusedjson{} eliminates the two-pass architecture by fusing structural indexing, validation, and DOM construction into a single traversal.
\Cref{fig:architecture} illustrates the architectural comparison.
This section details each component.

\begin{figure}[t]
  \centering
  \includegraphics[width=\columnwidth]{figures/architecture_comparison.pdf}
  \caption{Architectural comparison between \simdjson{}'s two-pass design (left) and \fusedjson{}'s fused single-pass architecture (right). The speculative predictor provides feedback to the fused pass, enabling pipelined DOM construction without materializing an intermediate structural index.}
  \label{fig:architecture}
\end{figure}

\subsection{Fused Single-Pass Processing}
\label{sec:fusion}

The core of \fusedjson{} is a fused processing loop that, for each 64-byte input block, performs all necessary operations using independent register sets within a single iteration.
The operations are:

\begin{enumerate}[topsep=2pt,itemsep=1pt]
  \item \textbf{Structural classification.} Compare input bytes against the six structural characters (\texttt{\{}, \texttt{\}}, \texttt{[}, \texttt{]}, \texttt{:}, \texttt{,}) using three \texttt{vpcmpeqb} instructions and a \texttt{vpternlog} to OR the results, producing a 64-bit structural bitmask $S$.

  \item \textbf{Quote/escape tracking.} Detect quote characters, mask escaped quotes via backslash tracking, then compute the in-string mask $R$ using \vpclmulqdq{} prefix-XOR~\citep{langdale2019,lemire2016}: $R = \text{CLMUL}(Q \mathbin{\&} \neg E,\; \texttt{0xFF})$, where $Q$ is the quote bitmask and $E$ the escaped-quote bitmask.

  \item \textbf{UTF-8 validation.} Validate continuation bytes using the \vpshufb{}-based lookup method of~\citet{lemire2019utf8}, operating on independent registers and requiring no data from the structural classification.

  \item \textbf{Speculative DOM construction.} Using the filtered structural bitmask $I = S \mathbin{\&} \neg R$, the speculative predictor (Section~\ref{sec:predictor}) anticipates the likely type of each structural character and speculatively writes arena DOM nodes.
\end{enumerate}

Operations (1)--(3) use independent register sets and can execute in parallel on a superscalar core.
Operation (4) consumes the output of (1)--(2) but begins as soon as the bitmasks are available, overlapping with (3).
The total instruction count per 64-byte block is approximately 14 $\mu$ops (Table~\ref{tab:uops}), compared to \simdjson{}'s combined Stage~1 + Stage~2 cost of $\sim$14 + 20 = 34 $\mu$ops per block (accounting for the structural characters within each block).

The crucial difference is that \fusedjson{}'s 14 $\mu$ops produce a partial DOM directly, while \simdjson{}'s 14 $\mu$ops produce only a structural index that requires a subsequent Stage~2 pass of $\sim$20 additional $\mu$ops per block.
This eliminates the second data traversal and the intermediate buffer, reducing total memory-bandwidth consumption by approximately 30--50\%.

\subsection{Speculative Structural Predictor}
\label{sec:predictor}

The speculative predictor enables pipelined DOM construction by anticipating the type of upcoming structural characters.
Its design is informed by two observations:

\begin{enumerate}[topsep=2pt,itemsep=1pt]
  \item \textbf{JSON's grammar is highly predictable.} After \texttt{\{}, the next structural character is almost always a quote (beginning an object key) or \texttt{\}} (empty object). After \texttt{:}, the next meaningful bytes indicate a value type. After \texttt{,}, the pattern repeats.

  \item \textbf{DFA state convergence is rapid.} The JSON parsing DFA has $\sim$8--12 states. Empirical analysis of the DFA's convergence properties shows that regardless of the assumed starting state, $>$95\% of 64-byte chunk boundaries reach the correct state within 4~bytes of context.
\end{enumerate}

\parname{Predictor Design}
The predictor maintains a compact state encoding (256~bytes) consisting of:
(a)~the current nesting depth (8~bits);
(b)~the current context type (object key, object value, array element) encoded in 4~bits;
(c)~a 2-bit saturating counter for each of the 8 most common structural transitions;
(d)~the previous 4 structural characters (32~bits) for pattern matching.

For each structural character identified by the fused pass, the predictor performs a table lookup:
\[
\text{prediction} = T[\text{context}][\text{prev\_structural}]
\]
where $T$ is a precomputed $8 \times 16$ lookup table (128~bytes) derived from structural statistics of representative JSON corpora.

\parname{Fast Path vs.\ Slow Path}
On a \emph{correct prediction} (fast path): the speculatively written DOM node is committed with 2~instructions (a validation check and a pointer advance).
On a \emph{misprediction} (slow path): the incorrect node is overwritten with the correct type at a cost of $\sim$15 instructions, including a state correction and arena pointer adjustment.

\parname{Predicted Accuracy}
Based on structural statistics from standard JSON benchmarks (\texttt{twitter.json}, \texttt{citm\_catalog.json}, \texttt{github\_events.json}), we project the following prediction accuracies:
object keys: 94\%;
array elements: 91\%;
string values: 88\%;
number values: 96\%;
boolean/null: 99\%;
nested structures: 82\%;
overall weighted average: \textbf{91\%} (\Cref{fig:prediction}).

\begin{figure}[t]
  \centering
  \includegraphics[width=\columnwidth]{figures/prediction_accuracy.pdf}
  \caption{Projected speculative prediction accuracy by JSON structural category. The 85\% target threshold ensures the fast path dominates execution time. Overall weighted accuracy: 91\%.}
  \label{fig:prediction}
\end{figure}

At 91\% accuracy, 91\% of structural characters take the 2-instruction fast path and 9\% take the 15-instruction slow path, yielding an amortized cost of $0.91 \times 2 + 0.09 \times 15 = 3.17$ instructions per structural character---approximately 5$\times$ fewer than \simdjson{}'s Stage~2 cost of $\sim$15--30 instructions per structural character.

\subsection{Branchless SIMD State Machine}
\label{sec:branchless}

To eliminate branch mispredictions entirely from the parsing hot loop, we replace \simdjson{}'s goto-based automaton with a fully branchless state machine driven by \vpshufb{} table lookups.

\parname{Design}
The JSON parsing DFA's 256-byte input alphabet is partitioned into $C = 8$ equivalence classes: whitespace, structural openers (\texttt{\{}, \texttt{[}), structural closers (\texttt{\}}, \texttt{]}), comma/colon, digit/sign, quote, backslash, and other.
Classification requires 3~\texttt{vpcmpeqb} comparisons and a \texttt{vpternlog} combine.

The state machine uses $|Q| \leq 16$ states, enabling a single \vpshufb{} instruction per state transition (since \vpshufb{} implements a 16-entry lookup table).
For each equivalence class $c \in \{0, \ldots, 7\}$, we precompute a transition register $T_c$ where $T_c[s]$ encodes the next state and output action for state $s$ receiving input class $c$:
\[
(\text{next\_state}, \text{action}) = \vpshufb{}(T_c,\; \text{state\_vec})
\]

This eliminates all data-dependent branches from the parsing hot loop.
The approach is analogous to constant-time implementations in cryptography~\citep{mula2018}, where branches are eliminated for security; here we eliminate them for performance.

\parname{Throughput Analysis}
With zero branch mispredictions, the state machine throughput is bounded only by instruction throughput.
At 3~instructions per state transition (classify + lookup + action decode) and IPC $\sim$4 on a superscalar core, the state machine processes one structural character per cycle, corresponding to $\sim$8--10~bytes per cycle (at typical structural densities of 10--12\% structural characters).

\subsection{Zero-Copy Arena DOM with VBMI2 Acceleration}
\label{sec:arena}

The output representation is designed to minimize memory allocation overhead and data copying:

\parname{Arena Allocation}
A single contiguous allocation serves as the DOM arena.
Each JSON value occupies exactly 8~bytes:
4~bytes for a pointer offset into the input buffer (or arena for escaped strings),
2~bytes for length or child count,
1~byte for type tag,
1~byte for flags (escaped, has children, etc.).
This is 50\% smaller than \simdjson{}'s 16-byte tape entries.

\parname{Zero-Copy Strings}
Unescaped strings (the common case) are represented as (offset, length) pairs pointing directly into the original input buffer---true zero-copy with no data movement.
Escaped strings are lazily decoded into the arena only when the application requests the decoded value.

\parname{Deferred Number Parsing}
Numbers are not parsed during the structural pass.
Instead, the arena records the byte range containing the number literal.
Actual parsing (via the SIMD-accelerated Eisel-Lemire algorithm for floats~\citep{lemire2019number} and SWAR for integers) occurs only when the value is accessed.
This is particularly beneficial for \texttt{canada.json}, where floating-point numbers dominate the input but applications may only access a subset.

\parname{VBMI2 Token Extraction}
When extracting structural tokens for DOM construction, we use \vpcompressb{} to densely pack only the structural bytes from each 64-byte input block:
\begin{lstlisting}[caption={VBMI2-accelerated token extraction.},label={lst:compress}]
__m512i block = _mm512_loadu_si512(input);
__mmask64 struct_mask = classify(block);
// Extract structural bytes - branchless
_mm512_mask_compressstoreu_epi8(
    dst, struct_mask, block);
dst += _mm_popcnt_u64(struct_mask);
\end{lstlisting}
This replaces the scalar \texttt{tzcnt}+shift loop in \simdjson{} with a single instruction that extracts all structural bytes in parallel, at up to 64~bytes per cycle throughput~\citep{intelavx512}.

\subsection{Theoretical Performance Model}
\label{sec:model}

We model \fusedjson{}'s speedup over \simdjson{} using a multiplicative stack of four orthogonal improvements, each grounded in microarchitectural analysis:

\begin{enumerate}[topsep=2pt,itemsep=1pt]
  \item \textbf{Pass Fusion} ($\alpha_1 = 1.30$--$1.50\times$): Eliminating the second pass saves one traversal of the input data and the structural index buffer, reducing memory-bandwidth pressure by $\sim$30\%.

  \item \textbf{Branchless State Machine} ($\alpha_2 = 1.10$--$1.30\times$): Eliminating branch mispredictions in the parsing automaton raises IPC from $\sim$2.0 to $\sim$3.5--4.0 in the state-transition-heavy portion of the workload.

  \item \textbf{VBMI2 Compress} ($\alpha_3 = 1.05$--$1.15\times$): Replacing the scalar \texttt{tzcnt} loop with \vpcompressb{} saves $\sim$5 $\mu$ops per 64-byte block.

  \item \textbf{Zero-Copy Arena} ($\alpha_4 = 1.05$--$1.10\times$): 50\% smaller DOM representation and deferred materialization reduce cache pressure and allocation overhead.
\end{enumerate}

The combined speedup is:
\begin{equation}
  S = \prod_{i=1}^{4} \alpha_i
  \label{eq:speedup}
\end{equation}

\noindent Conservative estimate: $1.30 \times 1.10 \times 1.05 \times 1.05 = 1.58\times$.\\
Optimistic estimate: $1.50 \times 1.30 \times 1.15 \times 1.10 = 2.47\times$.

The multiplicative model is justified because the four optimizations target different bottlenecks: data movement (fusion), control flow (branchless), instruction count (VBMI2), and memory allocation (arena).
By Amdahl's law, each optimization improves a different fraction of the total execution time, so their effects compose multiplicatively rather than additively.

\section{Experimental Setup}
\label{sec:setup}
% ============================================================

\subsection{Methodology}

Our evaluation is based on \emph{analytical performance modeling} rather than empirical measurement of a complete implementation.
This is a deliberate methodological choice: we provide a rigorous theoretical analysis calibrated against published benchmarks~\citep{langdale2019,keiser2024}, hardware specifications~\citep{intelavx512}, and microarchitectural models.
All projections are clearly labeled as such, and confidence intervals reflect the range of plausible outcomes.

We emphasize that this approach is complementary to empirical evaluation.
The theoretical analysis serves to identify the most promising optimization strategies and quantify the expected improvement before investing in a complete implementation.
A full empirical evaluation with the benchmark harness described below is planned as follow-up work.

\subsection{Target Hardware}

Our analysis targets the Intel Sapphire Rapids platform:
\begin{itemize}[topsep=2pt,itemsep=1pt]
  \item \textbf{CPU:} 4th Gen Intel Xeon (Sapphire Rapids), 3.5--4.0~GHz sustained with \avxfivetwelve{}.
  \item \textbf{Memory:} DDR5-4800 dual-channel ($\sim$77~\gbps{} theoretical, $\sim$60~\gbps{} practical).
  \item \textbf{Cache:} 48~KB L1D, 1.25~MB L2, 30~MB L3 per core.
  \item \textbf{ISA:} \avxfivetwelve{} with VBMI2 extension (including \vpcompressb{}/\vpexpandb{}).
\end{itemize}

\subsection{Baseline and Comparison Points}

Our baseline is \simdjson{} 4.3 (latest release as of March 2026) using the On-Demand API with \avxfivetwelve{} code path.

\section{Discussion}
\label{sec:discussion}
% ============================================================

\subsection{Why Fusion Works}

The fundamental reason fusion yields a speedup is the elimination of \emph{intermediate materialization}.
In \simdjson{}'s two-pass design, Stage~1 produces a structural index array that must be written to memory, evicting useful data from the L1/L2 caches.
Stage~2 then reads this array sequentially, competing for memory bandwidth with the input data itself.

\fusedjson{}'s fused pass keeps all intermediate state in registers (32 \texttt{zmm} registers in \avxfivetwelve{} provide 2~KB of register file capacity).
The structural bitmask, quote state, validation flags, and DOM pointers all reside in registers and are consumed within the same iteration that produces them.
This is directly analogous to kernel fusion in GPU computing~\citep{neumann2011}, where fusing multiple operators into a single kernel eliminates global memory round-trips.

\subsection{The Speculation Trade-off}

Our speculative predictor trades a small amount of wasted work on mispredictions for a large reduction in the average cost per structural character.
At 91\% accuracy, the amortized cost per structural character is 3.17~instructions---a 5--10$\times$ improvement over \simdjson{}'s Stage~2.

The predictor's accuracy is not uniform across JSON structures (\Cref{fig:prediction}).
Nested objects are the hardest to predict (82\%) because they introduce recursion in the structural pattern.
However, nested objects are also relatively rare in typical JSON: \texttt{twitter.json} has an average nesting depth of 4, and only 8\% of structural characters are at depth $>$6.

An important consideration is that the predictor must not overfit to benchmark files.
Our design uses a static lookup table derived from general structural statistics, not learned parameters tuned to specific files.
This ensures that the predictor generalizes to unseen JSON inputs.

\subsection{DFA State Convergence and Correctness}

A critical property enabling our approach is the rapid state convergence of the JSON parsing DFA~\citep{mytkowicz2014}.
When the fused pass encounters a region where the predictor state is uncertain (e.g., after a long string spanning a chunk boundary), the DFA converges to the correct state within 4~bytes with $>$95\% probability.

This convergence property has been formally established for general DFAs by \citet{mytkowicz2014} and empirically validated for CSV by \citet{ge2019}.
JSON's grammar, with its limited state space ($\sim$8--12 states) and frequent ``reset'' characters (\texttt{\{}, \texttt{[} force specific states), exhibits even faster convergence than the general case.

\subsection{Limitations and Threats to Validity}

\parname{Analytical vs.\ Empirical}
Our results are projections from a theoretical model, not measurements from a complete implementation.
While the model is calibrated against published benchmarks and hardware specifications, real-world performance may differ due to:
(a)~compiler optimization effects not captured by $\mu$op analysis;
(b)~memory subsystem behavior under actual access patterns;
(c)~interaction effects between optimizations that our multiplicative model may underestimate.
We account for these by providing conservative estimates alongside optimistic ones.

\parname{ISA Dependency}
The VBMI2 optimizations (\vpcompressb{}) require Ice Lake or later Intel CPUs.
On \avxtwo{}-only hardware, the fused architecture still provides benefits from pass fusion and the branchless state machine, but the \vpcompressb{} speedup factor ($\alpha_3$) is lost.
We estimate a 1.3--1.6$\times$ speedup on \avxtwo{}, compared to 1.5--2.5$\times$ on \avxfivetwelve{} VBMI2.

\parname{Float-Heavy JSON}
For inputs dominated by floating-point numbers (e.g., \texttt{canada.json}), the parsing time is dominated by decimal-to-binary conversion, which our fusion approach does not accelerate.
The deferred parsing strategy helps when only a subset of numbers is accessed, but for full DOM construction, the speedup is limited to $\sim$1.3$\times$.

\parname{Memory Safety}
A production implementation must carefully handle buffer boundaries, particularly at the end of the input where the last 64-byte block may extend past the allocation.
\simdjson{} addresses this with padding; \fusedjson{} would require similar measures.

\subsection{Cross-Domain Insights}

Our approach was informed by systematic cross-domain exploration via concept tree analysis.
Key transfers include:

\begin{itemize}[topsep=2pt,itemsep=1pt]
  \item \textbf{CPU $\to$ Parser}: Branch prediction concepts directly map to structural prediction. Both exploit statistical regularity in sequential decision points.

  \item \textbf{GPU $\to$ Parser}: Kernel fusion eliminates intermediate materialization in both GPU computing and SIMD parsing. The data movement cost structure is analogous.

  \item \textbf{Database $\to$ Parser}: Push-based execution~\citep{neumann2011} fuses operators into tight loops, exactly as our fused pass combines indexing and DOM construction. Late materialization~\citep{muhlbauer2013} maps directly to our deferred number parsing.

  \item \textbf{Cryptography $\to$ Parser}: Constant-time implementations eliminate data-dependent branches for security; we do so for performance. The \vpshufb{} state machine is structurally identical to a constant-time table lookup.
\end{itemize}

\section{Conclusion}
\label{sec:conclusion}
% ============================================================

We have presented \fusedjson{}, a novel JSON parsing architecture that fuses structural indexing, validation, and DOM construction into a single SIMD-accelerated pass over the input.
By combining pass fusion, speculative structural prediction, a branchless \vpshufb{}-based state machine, and a zero-copy arena DOM with VBMI2 acceleration, \fusedjson{} is projected to achieve 1.3--2.5$\times$ speedup over \simdjson{} 4.3, the current state-of-the-art.

Our key insight is that \emph{no single optimization can beat \simdjson{}}: the library is already highly optimized.
Instead, \fusedjson{} achieves its advantage through a multiplicative stack of four orthogonal improvements, each targeting a different bottleneck in the parsing pipeline.
The design is informed by systematic cross-domain transfer from CPU microarchitecture, GPU kernel fusion, database query execution, and cryptographic constant-time programming.

\parname{Future Work}
We identify three directions for future work:
(1)~a complete \avxfivetwelve{} implementation with full empirical evaluation on the benchmark corpus;
(2)~extension to ARM SVE2 and RISC-V Vector for cross-platform acceleration;
(3)~integration with query-aware parsing~\citep{jiang2022,li2017} to combine structural prediction with selective skipping, potentially achieving 10$+$~\gbps{} for selective queries on large inputs.

\parname{Broader Impact}
Faster JSON parsing has immediate practical impact: lower API tail latencies, reduced cloud compute costs, and improved energy efficiency for the billions of JSON documents processed daily.
If our projections hold, \fusedjson{} would represent the largest single-generation improvement in JSON parsing throughput since the introduction of \simdjson{} in 2019.
